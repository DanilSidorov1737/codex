# Reviewed finite autonomy, discussion and knowledge

Tasks 10–15 extend the existing series, controls, handoffs, notes and report
snapshot. They introduce no dependency, provider calls, new worker service or
unbounded authority. Implementation and fresh native qualification pass; see
[operations native qualification](operations-native-qualification.md) for the
actual scopes, receipts, failures and recovery boundaries. Read next-twenty.md and status.md for the actual checkpoint.

## Finite goal policy

Y on a saved template previews a finite series. Selecting the linked goal option
captures the exact goal/revision, work-type label, template, projects, model
scopes, participants, role/node versions, finite run count, deadline and shared
resource pool. The label describes the owner's intended work; it is not a model
classifier or an authorization rule. Existing native scopes enforce authority.

A policy persists independently of the frontend. `*` pauses, resumes or revokes
its admissions and future invocations through versioned controls. Pause can park
quiescent work; already admitted receipts finish and remain charged. Goal changes
fence further admissions. Accepted work, prior grants, control history and usage
remain. Changing policy content requires reviewing a new finite policy; cancelling
the old policy does not refund its usage. No root acceptance or Apply is automatic.

Migration 15 is a schema compatibility floor. Older migrators refuse this store
instead of silently ignoring its supervision/retrieval semantics. It adds no new
ledger and leaves existing grants usable by this runtime.

## Checkpoint replanning

`&` on a blocked task drafts a reasoned replacement using its exact verified
checkpoint and captured eligible receiver. Saving records a versioned proposal
and starts no work. F11 exposes it; `%` confirms its precise pending revision.
The native API supports 1–32 distinct replacements; the current form drafts one.

Application verifies actual checkpoints, then performs all native handoffs in one
transaction. A stale receiver, unavailable checkpoint, live worker/descendant,
unknown usage/effects or exhausted original limit refuses the complete delta.
The original grant, remaining budgets and deadline stay attached; accepted tasks
are preserved. An applied proposal is immutable and cannot be replayed. Failures
without a trustworthy checkpoint need reconciliation rather than this continuation.

## Finite agent discussions

`+` saves a typed discussion template: 1–8 arbitrary distinct participants,
1–3 rounds and one conclusions author. It starts no work. The ordinary workflow
preview separately reviews each model, input/output scope, checks, approvals and
finite request/token authority. At most 25 contribution/conclusion tasks result.

Each later round waits for acceptance of the previous round. Input paths are
prefilled from direct predecessors, but only accepted contributions permitted by
the captured scope are imported. Contributions record position, evidence,
agreements, dissent and follow-up proposals. Conclusions preserve disagreement
and uncertainty. These are reviewable artifacts, not consensus guarantees or new
execution authority. Editing this template with ordinary Put intentionally turns
it into an ordinary workflow and removes the typed discussion metadata.

## Knowledge maintenance

`-` on a memory-search result or selected F11 knowledge control retires/restores
an exact body hash with a reviewed reason and control revision. Retrieval filters
retired notes before matching/pagination, retaining project/agent/team membership
and superseded-note boundaries. Owner-only `organization list notes` exposes
history. Retired notes cannot be promoted until restored; O creates reviewed
corrections/promotions using the existing provenance rules. Restoration grants
only the original visibility. Prior admitted context and history are retained.
Duplicate/conflict judgments remain explicit owner review, not a new classifier.

## Captured evidence scorecards

Z (or z on a selected project/agent/run) shows scorecards grouped by the captured
attempt owner/provider/model, project and workflow. Current handoff recipients do
not rewrite historical attribution. Counts cover accepted results, terminal
failures/blockers/uncertainty, real check outcomes and recorded usage across the
whole report snapshot, independently of the task page. Correlated check queries
prevent multiplied token counts. A response bounds groups at 2,000 and reports
truncation; narrow to a project or inspect paginated history when needed.

Missing historical dimensions or an older daemon's missing scorecards remain
unavailable. No quality score, invoice, hardware reading or automatic fallback is
invented. Request counts and reported-token limits retain their documented
in-flight and unknown-usage limitations.
